## 研究点状态路由

研究点卡片的 `status` 是科研状态唯一真源；这里仅规定后续流程，不复制各卡片状态。`framework_adoption` 独立记录主框架采纳决策。

| 研究状态 | 调度后续工作流 |
| --- | --- |
| `draft` | 补全假设、最小实现边界、验证协议，决定是否激活。 |
| `active` | 连接论文、代码、EXP/REPRO 证据；保持单变量与可复现。 |
| `validated` + `not_assessed` / `pending_decision` | 进入“框架采纳决策”：先询问用户是否更新基础框架。 |
| `validated` + `adopted` | 对齐 `02框架信息.md`、调度和索引，记录框架版本。 |
| `validated` + `deferred` / `superseded` | 保留证据，等待用户重新开启决策或沿链接检查替代项。 |
| `paused` / `rejected` | 保留理由与证据；只有新的明确证据才重新进入评估。 |

## validated 研究点的框架采纳工作流

1. 运行 `scheduler.py next --id RP-0001`，汇总关联 EXP、REPRO、代码、配置和证据；它不改文件。
2. 调度首先询问用户：是否把该 `validated` 研究点采纳到基础框架？
3. 若用户愿意，先给出最小修改计划：必改 [[02框架信息.md]]，同步本节“当前主框架”；仅在事实变化时再更新 `00基本信息.md`、`01约束文件.md`、`03研发经验.md` 或 README。
4. 再次取得用户对该文档修改计划的同意，才执行写入；写后记录版本、RP 链接与采纳日期，并运行 `align`/引用扫描。
5. 最后用 `research_point.py framework --decision adopted ...` 记录采纳。延后则记录 `deferred`，被后来框架替代则记录 `superseded`。

## 待框架采纳决策

此队列由 `scheduler.py queue` 从 RP 卡片派生；禁止手工复制完整卡片状态。
